# 架构说明

本文说明代码怎么分工、数据怎么流动，以及几处关键的设计取舍。使用方法见 [README](../README.md)。

## 整体结构

一个 Python 进程同时承担全部后端工作：采集音频、识别、分析、存储，并通过本机 HTTP 接口和 WebSocket 把数据交给界面。界面是 React 写的网页，由系统自带的网页引擎显示在桌面窗口里（pywebview：Windows 用 WebView2，macOS 用 WKWebView），也可以直接用浏览器打开。

```text
┌────────────── 桌面窗口 / 浏览器（frontend/，React）──────────────┐
│ 盯播 │ 话术框架 │ 历史复盘 │ 设置                                    │
└──────────────┬──────────────────────────────▲──────────────────────┘
               │ HTTP（读写数据、开播停播）     │ WebSocket /api/events（实时事件）
┌──────────────▼──────────────────────────────┴──────────────────────┐
│ api.py（FastAPI，只监听 127.0.0.1，需要启动令牌）                       │
│   app.Services：Storage · SessionManager · EventBus · ModelDownloads   │
│                      │                                                │
│   monitor/session.py：MonitorSession（一场盯播）                         │
│     采集线程 ──有界队列──► 处理线程 ──► 大模型审核线程                      │
│     audio/*            asr/*  analysis/*        analysis/llm.py         │
│                      │                                                │
│   storage.py：SQLite（话术框架、场次、转写、报告、提醒、设置）              │
└──────────────────────────────────────────────────────────────────────┘
```

## 一场盯播的数据流

1. **采集线程**从音频来源读 0.1 秒一块的音频，放进有界队列；开了录音时，入队前先写进录音文件。
2. **处理线程**加载识别引擎后逐块识别，得到两类事件：`partial`（正在说的这句话，会被更新）和 `final`（定稿的一句话）。有人说了话但没认出字时，`final` 的文字为空，只用来计算说话时间和停顿。
3. 每句定稿的话先经过 `FrameworkAnalyzer.inspect`：命中的要点、违规表达、口头禅和字数只算这一次，结果存进会话历史。违规表达立即生成提醒。
4. 处理线程按**音频时间**调度窗口分析：每隔 `interval` 秒分析过去 `window` 秒，汇总语速、说话占比、冷场、口头禅和要点覆盖，生成窗口报告。
5. 窗口报告里新出现的问题变成提醒；开启了大模型审核时，把这段转写交给审核线程。
6. 停止或音频结束时，补一份最后不满一个周期的窗口报告，再对全场做一次总结。
7. 句子、报告、提醒逐条写入 SQLite，同时通过事件总线推给界面。界面断线重连时先收到 `hello`（当前场次的完整快照），再接着收增量事件。

WebSocket 事件类型：`hello`、`state`、`level`（输入电平）、`partial`、`segment`（定稿句子和高亮）、`report`、`summary`、`alert`、`llm`（审核结果）、`health`（积压、丢弃、有无信号）、`model`（模型下载进度）、`logins`（登录窗口开没开、登录信息何时保存）。

## 关键设计取舍

**按音频时间调度，而不是墙上时钟。** 窗口分析、冷场判断、提醒时间都以“已处理的音频样本数”为准。这样回放文件和实时采集走同一套逻辑：文件可以几秒内分析完，结果与按实际速度播放一致；测试也可以用确定性的音频块和脚本识别器验证整条流程。

**每句话只分析一次，窗口只做汇总。** 关键词匹配在句子到达时完成，窗口分析只累加已有结果，所以“每分钟分析过去 5 分钟”乃至全场总结的开销都很小。

**规则为主，大模型为辅。** 关键词规则结果确定、能给出原话和时间，可以即时提醒；大模型用来补充语义层面的问题（说错价格、讲得含糊），是可选的第二层：
- 模型引用的原话会回到转写里逐字核对，对不上的不提醒；
- 规则已经提醒过的违规词、已判定没讲的要点，模型再说一遍时不重复提醒；
- 模型把识别错字当成问题时直接丢掉；
- 百炼上的千问 3 默认开启深度思考，实测一次审核约 70 秒，关闭后约 13 秒，所以对百炼地址固定关闭；
- 实时盯播时上一轮审核没做完就跳过本轮，免得结果越积越旧；分析文件时排队逐个审核。

**窗口未满不判“没讲”。** 开播头几分钟，窗口还没达到设定长度，此时没提到某个要点只是“还没讲到”，不报问题；全场总结则按整场判断。

**录音和盯播共用一条时间轴。** 录音在采集线程里、入队之前写，内容是设备送来的全部声音，包括识别跟不上时被丢弃的部分；被丢弃的部分在识别那边用等长静音补上，所以录音里的第 t 秒就是盯播的第 t 秒，复盘页上转写、提醒的时间可以直接跳到录音对应位置。每次写入都会更新 WAV 文件头并写到磁盘，程序中途退出时已录下的部分也能播放。只录实时来源：音频文件本来就在磁盘上，用录音“重新分析”时也不会再录一份。录音出错（例如磁盘满）只提醒一次，盯播照常进行。

**实时来源积压时丢最旧的音频，文件来源不丢。** 声卡和直播流不会等人，识别跟不上时队列会积压。实时来源丢弃最旧的音频块，用等长静音补上以保持时间轴不变，并提醒用户这段没有分析；文件来源则让采集等待，保证不漏。

**直播间链接靠网页自己的播放器，不对接各平台接口。** 各平台取直播流的接口经常改，还要签名，逐个对接维护不过来。现在的做法是：用电脑上的 Edge 或 Chrome（无界面模式、临时资料目录）打开直播间，网页播放器自己会去取流。
- 播放器请求了 flv/m3u8（抖音、快手、B 站、斗鱼）：记下最初请求的地址（跳转后的地址常常只能用一次）和 Referer、User-Agent，关掉浏览器，由 PyAV 直接拉流。CDN 会校验这两个请求头。拉流和浏览器一样走系统代理，否则开着代理软件时，有的 CDN 节点只有经代理才连得上。
- 没有这类地址（虎牙走 P2P 和 WebRTC）：浏览器继续播放，网页加载前注入的脚本把 `<video>`/`<audio>`（只取 MediaStream 和 blob: 来源）以及网页接到扬声器上的 Web Audio 节点汇到一个 16 kHz 的 AudioContext，约每 0.26 秒经 CDP 绑定把 PCM 送回。网页一时没声音就补静音，保持时间轴，让“没有收到声音”的提醒照常工作。后台浏览器的网页可能被判为不可见（新资料目录会弹出 Edge 的同步确认页），有的播放器会因此静音，所以启动时关掉同步和后台降速，脚本里也让网页始终以为自己在前台。
- 要登录才能看的直播间（例如淘宝直播）：用户点“登录平台账号”，程序用一个固定的资料目录打开**有界面**的浏览器窗口，用户在里面登录。窗口开着时每 2 秒经调试协议读一次全部 Cookie 存到本机；后台浏览器打开直播间前先放入这些 Cookie。不直接让后台浏览器用登录窗口的资料目录，是因为：同一个资料目录同时只能被一个浏览器进程使用，登录窗口开着就会冲突；很多网站的登录 Cookie 是会话 Cookie，浏览器一关就从资料目录里消失。所以 Cookie 由程序自己保存（Windows 上用 DPAPI 加密），再次打开登录窗口时也先放回去，才能保持登录。
- 打开直播间放在建场次之前（几秒到二十几秒），打不开就直接报错，不留下一场空记录。断流时先重连原地址，不行再重新打开网页拿新地址，都失败就提醒“直播可能已经结束”并正常收尾。来源发现的这些情况通过 `take_notices()` 变成系统提醒。
- 用的是系统自带的浏览器，打包成 exe 也不需要额外安装；没有浏览器、需要登录或没有网页版的直播，用“系统声音”。

**没有网页版的直播靠“只听一个程序”。** 视频号这类只能在电脑客户端（或投屏到电脑的手机画面）里看的直播，不逐个对接，而是只采集播放它的那个程序的声音（Windows 11 的按进程回环采集：`ActivateAudioInterfaceAsync("VAD\Process_Loopback")`，带上子进程）。
- 程序列表来自各播放设备上的音频会话。浏览器、微信的声音其实由子进程播放，所以每个会话沿父进程往上找到用户启动的那个程序（到资源管理器、系统服务为止；父进程比子进程启动得晚，说明进程 ID 被重新用过，也停下），采集时包含它的整个进程树。不列出本程序自己（界面提示音）。
- 系统直接按 16 kHz 单声道 16 位送来；程序不出声时照样送静音，时间轴不断。实测只采得到送往默认播放设备的声音，送到其他设备时只有静音，所以这个来源的“没有收到声音”提醒会提示检查输出设备。程序退出后提醒并正常收尾。
- 用 ctypes 按虚函数表的位置调用 COM 接口，不新增依赖，打包也不用额外处理。Windows 10 没有这个系统接口，界面上只显示“整个播放设备”。

**提醒去重。** 窗口分析的问题只在第一次出现时提醒，持续存在不重复，消失后再出现才再提醒；违规和冷场在发生时提醒一次；大模型的问题按“同一句原话”或“同一类别”去重。

**本地优先。** 默认的识别引擎在本机运行；讯飞和大模型都是可选的云服务。数据全部存在本机 SQLite，场次里保存开播时话术框架的完整副本，之后修改框架不影响历史记录。

**本地服务的安全边界。** 服务只监听 127.0.0.1；每次启动生成随机令牌，放在网址 `#` 之后（不会发给服务器、不进日志），接口请求要带上。浏览器的 WebSocket 和 `<audio>` 元素没法加请求头，所以只有 `/api/events` 和录音地址 `/api/sessions/{id}/audio` 接受 `?token=`。同时检查 Host 头，防止网页借 DNS 重绑定访问本地接口；录音路径由场次 ID 拼出，ID 先按 `[A-Za-z0-9_-]` 校验，拼不出数据目录以外的路径。

**桌面外壳用 pywebview，暂不用 Tauri。** 整个后端就是一个 Python 进程，pywebview 直接在同一进程里打开系统网页引擎窗口，不需要 Rust 工具链和额外的进程间通信。运行时需要的 Python 环境由 PyInstaller 一起打进安装包（见下面“安装包”）。

**同一个数据库只有一个主实例。** 双击两次图标会开出两个程序，后开的那个启动时会把前一个正在盯的场次当成异常退出留下的、标成“已中断”。主实例拿着数据库文件夹里 `running.lock` 的文件锁（`instance.py`，Windows 用 `msvcrt.locking`，macOS 用 `flock`，进程退出时系统自动放开）；再打开桌面程序时弹出“已经打开了”的提示就退出。命令行的 `analyze` 不是主实例时照常分析，只是不去改别的场次的状态。

**数据库升级用 `PRAGMA user_version`，暂不用 Alembic。** 只有一个本地 SQLite 文件、表结构简单，按版本号顺序执行迁移函数就够了；`storage.py` 的 `_MIGRATIONS` 里追加一步即可升级旧数据。

## 安装包

- **PyInstaller 打成文件夹**（`packaging/voicedetect.spec`）：Windows 是 `AI盯播助手/VoiceDetect.exe` 加 `_internal`，macOS 再包成 `AI盯播助手.app`。不打成单个 exe：单个 exe 每次启动都要先把一百多 MB 解压到临时目录，慢，也容易被杀毒软件拦。sherpa-onnx 的原生库要显式收进来，界面构建结果和内置资源按原来的包内路径放，`importlib.resources` 照常能找到。exe 的“文件说明”写成“AI 盯播助手”，任务管理器、音量合成器里显示这个名字。
- **Windows 安装程序**用 Inno Setup（`packaging/installer.iss`）：按当前用户装在 `%LOCALAPPDATA%\Programs`，不弹管理员权限确认；升级时先删旧的 `_internal`；卸载不删数据目录。**macOS** 做成 dmg，里面放一个“应用程序”的快捷方式，拖进去就装好了；Info.plist 里写了麦克风用途说明，没有它 macOS 不让用麦克风。
- 都**没有签名**：Windows 会提示“已保护你的电脑”，Mac 要到“隐私与安全性”里允许。签名需要付费证书，以后再定。
- **没有命令行窗口**：双击打开的程序 `sys.stdout`、`sys.stderr` 是 `None`。uvicorn 默认的日志格式化器会去问命令行支不支持颜色而直接出错，所以本地服务不让 uvicorn 配置日志（警告照常写进日志文件），`main()` 也把它们换成丢弃输出的文件；桌面程序启动出错时弹出提示框，不悄悄退出。
- **WebView2**：Windows 11 自带，Windows 10 一般随新版 Edge 装好。没有它时 pywebview 会退回 IE 内核、界面显示不出来，所以启动前查一下注册表，没有就用默认浏览器打开界面；这时网页关掉一分钟（又没有在盯播）程序自己退出。
- **自动打包和检查**（`.github/workflows/package.yml`）：在 GitHub 的 Windows、Mac（Apple 芯片）、Mac（Intel）机器上各打一份，先装上（Windows 静默安装）再跑 `packaging/check_app.sh`：用打包好的程序分析演示音频，再用 `selfcheck` 打开真的桌面窗口，等界面显示出来、从本地服务读到版本号再关掉。推送 `v` 开头的标签时发布到 Releases。`VOICEDETECT_DEVTOOLS_PORT` 可以打开窗口里网页引擎的调试端口，本机检查打包后的窗口用，平时不设。

## 识别引擎

| | SenseVoice（本地） | 讯飞实时转写（云端） |
| --- | --- | --- |
| 运行方式 | sherpa-onnx 在 CPU 上运行 SenseVoice int8 模型，Silero VAD 切句 | WebSocket 连接 `rtasr.xfyun.cn`，每 40 毫秒发送 1280 字节 PCM |
| 出字方式 | 一句话说完（停顿约 0.4 秒）定稿；说话过程中每隔 0.5–2 秒把这句话到目前为止的音频再识别一次，作为正在识别的文字 | 服务端推送中间结果和定稿结果 |
| 实测速度 | 5.6 秒音频解码约 0.09 秒；173 秒的演示音频整段分析约 4 秒 | 每句话说完后约 1 秒返回（30 秒样本） |
| 费用 | 免费，首次下载约 240 MB | 按时长计费 |

## 存储

一个 SQLite 文件（WAL 模式），表：`frameworks`（框架 JSON）、`sessions`（场次、框架副本、全场总结）、`segments`（转写）、`reports`（窗口报告 JSON，含审核结果）、`alerts`（提醒 JSON）、`settings`（应用设置 JSON）。程序异常退出时仍标记为进行中的场次，下次启动会改为“已中断”。

录音不进数据库：存在数据目录的 `recordings/<场次ID>.wav`（16 kHz 单声道 16 位，约每小时 115 MB），有没有录音看这个文件在不在；删除场次时一起删除。

直播平台的登录信息也不进数据库：`logins/cookies.bin` 是登录窗口里的全部 Cookie（JSON，Windows 上经 DPAPI 加密），`logins/profile` 是登录窗口的浏览器资料目录；“清除登录信息”删除整个 `logins` 文件夹。

## 测试

- `tests/test_text.py`、`test_matcher.py`、`test_window.py`：数字读法、同音匹配、每条分析规则的预期结果。
- `tests/test_session.py`：用脚本识别器和合成音频块测试实时会话的调度、积压丢弃、冷场与无信号提醒、去重、大模型审核接入、录音（含被丢弃的音频、录音失败不影响盯播）和快照恢复。
- `tests/test_recording.py`：WAV 在录音进行中就能读出完整长度；场次 ID 不能拼出目录外的路径。
- `tests/test_api.py`：HTTP 接口和 WebSocket 的完整开播流程、鉴权和输入校验；实时来源会录音、文件不录、录音地址的令牌和 Range 请求、删除场次时删除录音。
- `tests/test_room.py`：本机起一个模拟直播间网站，用真实的 Edge/Chrome 打开：fetch flv 的网页走直接拉流（CDN 要求 Referer，断开后自动重连），Web Audio 和 `<audio>` 出声的网页走从网页取声音（被挤到后台也不静音），没开播的网页给出提示；没有浏览器时跳过这几项。
- `tests/test_apps.py`：同时启动两个播放不同频率正弦波的程序（很轻，-50 dBFS），只采集其中一个时另一个的声音低 40 dB 以上；程序列表里有它且标为正在出声；程序退出后来源结束并提醒；父进程归并规则用构造的进程表测试。需要 Windows 11 和播放设备，否则跳过。
- `tests/test_logins.py`：模拟网站的直播间要带着登录页发的会话 Cookie 才有直播：未登录时打不开，在登录窗口（测试时用无界面模式）登录一次后能直接拉流；重开登录窗口仍是登录状态；清除后 Cookie 和资料目录都删掉；Cookie 文件在 Windows 上不是明文。
- `tests/test_instance.py`：另一个进程拿着锁时拿不到；不是主实例时不把别人进行中的场次标成“已中断”；浏览器模式在网页关掉、盯播结束后自己退出。
- `tests/test_desktop.py`：没有命令行窗口（`sys.stdout` 为 `None`）时本地服务照样能起来，命令照样能跑。
- `tests/test_xfyun.py`：用本地 WebSocket 服务器模拟讯飞协议（签名用官方文档示例核对）。
- `tests/test_llm.py`：用模拟的 HTTP 服务测试提示词、结果解析和错误提示。
- `tests/test_sensevoice.py`：用真实模型跑演示音频，检查能抓到预设的违规词、冷场和漏讲（未下载模型时跳过）。
- `frontend/src/*.test.ts`：时间格式、高亮切分、实时事件合并。
- **自动测试**（`.github/workflows/test.yml`）：每次推送都在 GitHub 的 Windows 和 Mac 机器上跑上面全部测试（含真实识别和真实浏览器），通过、失败、跳过的数量和跳过原因写在运行页面的标注里。
